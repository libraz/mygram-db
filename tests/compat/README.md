# Persistence compatibility corpus

`corpus/` holds byte-exact persistence artifacts that the current code must keep
being able to read. `persistence_corpus_test.cpp` loads every one of them
through the real public read path and asserts on the content that comes back.

The formats and the version-acceptance policy these fixtures pin are described
in `spec/persistence-formats.md`.

## Why the fixtures are never regenerated

The test only reads `corpus/`. Nothing in a normal test run writes to it.

A fixture regenerated by the code under test proves nothing: it would show that
the current writer and the current reader agree, which every round-trip test in
the suite already covers. The value of these files is that their bytes were
frozen before the change you are about to make.

`generate_compat_corpus` is built by the normal build so that it keeps
compiling, but it is not registered as a test and is never invoked by `ctest`.
Running it is a deliberate act:

```
./build/bin/generate_compat_corpus tests/compat/corpus
```

Two of the fixtures come out of the real dump writers, and their bytes change on
every run even when nothing else changed: the header carries a wall-clock
timestamp, and the embedded index and document store payloads are emitted in
hash-map iteration order, which is not stable between runs. Two consecutive runs
of the same binary therefore differ. That is expected; do not commit such a diff
unless you meant to replace the fixture, and do not use a byte comparison
against a fresh run to decide whether the writers changed.

## What to do when a fixture stops loading

Treat it as a compatibility break, not as a broken test.

A failure here means an artifact an earlier release wrote can no longer be
read. Narrowing the set of readable artifacts is an externally visible change
to the product, so the question is whether that change was intended — not how
to make the test green. Only edit a fixture or its expectation once the break
has been decided on deliberately, and say so in the release notes.

If the change was not intended, the fix belongs in the read path.

## Synthetic fixtures and release fixtures

The distinction matters when reading a failure.

**Synthetic** fixtures are assembled byte by byte by `generate_corpus.cpp` from
the layout in `spec/persistence-formats.md`. A synthetic fixture that stops
loading means the read path diverged from the documented layout — or that the
documented layout was wrong.

| Fixture | Format | Version |
|---|---|---|
| `index_v1.mgix` … `index_v4.mgix` | index payload | 1, 2, 3, 4 |
| `index_v5_unsupported.mgix` | index payload | 5 (must be refused) |
| `docstore_v1.mgds` … `docstore_v3.mgds` | document store | 1, 2, 3 |
| `docstore_v4_unsupported.mgds` | document store | 4 (must be refused) |
| `dump_v1_meta_v1.dmp` | container 1, metadata 1, index 1, docstore 1 | |
| `dump_v2_legacy_payloads.dmp` | container 2, metadata 2, index 3, docstore 2 | |
| `dump_v2_meta_v3_unsupported.dmp` | container 2, metadata 3 (must be refused) | |
| `dump_v3_unsupported.dmp` | container 3 (must be refused) | |

Two further fixtures are produced by the current writers, because the current
code can still emit those versions: `dump_v1_meta_v2.dmp` (`WriteDumpV1`) and
`dump_v2_current.dmp` (`WriteDumpV2`).

**Release** fixtures were produced by an earlier release's own dump writer,
built from that release's source tree. Their content follows that release's
defaults rather than this directory's manifest, and no current code path can
reproduce their bytes. A release fixture that stops loading means a dump a user
may actually be holding has become unreadable.

| Fixture | Written by | Container | Index | Document store | Compatibility metadata |
|---|---|---|---|---|---|
| `release_v1_3_2.dmp` | v1.3.2 | 1 | 1 | 1 | none |
| `release_v1_5_4.dmp` | v1.5.4 | 1 | 2 | 2 | none |
| `release_v1_6_1.dmp` | v1.6.1 | 2 | 2 | 2 | none |
| `release_v1_9_0.dmp` | v1.9.0 | 2 | 4 | 3 | 1 |

`release_v1_3_2.dmp` does not load. Its header and config section decode, but
that release wrote its posting lists with the octets in the reverse order and
the artifact does not record which order was used, so the index payload cannot
be decoded. The test asserts the refusal explicitly and explains it; see
`ReleaseDumpCorpusRejectionTest`.

## Adding a fixture for a new format version

1. Add the file name and any new expectation to `corpus_manifest.h`. Both the
   generator and the test read that header, so the bytes written and the content
   asserted stay in one place.
2. Add a builder to `generate_corpus.cpp` next to the nearest existing one, with
   the field offsets commented against `spec/persistence-formats.md`. Assemble
   the bytes explicitly rather than calling a writer, unless the version is one
   the current code still emits.
3. Run the generator, and commit both the generator change and the produced
   bytes.
4. Add the fixture to the parameter list of the matching test. A fixture that
   only asserts "the load returned success" is not worth adding: assert the
   document count, the primary keys and a term that has to be findable.

A version the current code refuses gets a fixture too. Assert the exact error
code, not just that the load failed.
