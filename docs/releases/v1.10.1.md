# MygramDB v1.10.1 Release Notes

**Release Date:** 2026-08-27
**Type:** Correctness, Fail-Closed Replication & Cross-Surface Consistency
**Previous Version:** v1.10.0

---

## Overview

Every change in this release is corrective. Nothing here is a new capability, no configuration key was added, and no default was chosen for a reason other than matching something the project had already promised.

The theme is that the same rule was implemented more than once and the copies had drifted. Search returned different documents depending on which of four internal paths served the query. HTTP validated a request differently from TCP. The initial load decided which rows belong in the index by one rule and replication decided by another. A binlog event nobody had classified was skipped rather than refused. In each case the correction was to make one rule, in one place, and let every caller read it.

Because these are corrections rather than redefinitions, they ship in a patch release. But several of them change what a client receives or whether a configuration starts, and a few of them will make a deployment that looked healthy start reporting an error. Those are listed below, and the ones that need action before upgrading are marked.

**Highlights:**

- **Replication refuses what it cannot apply** — an event type nobody classified now stops the stream instead of being skipped, which closes a family of silent divergences
- **One search answer** — the four execution paths, and the two protocol surfaces, return the same documents for the same query
- **Old dumps load again** — dumps written by v1.5.4 through v1.9.0 restore, as the v1.10.0 notes said they would
- **Bounded request cost** — highlighting, boolean exclusion, threshold search and `INFO` no longer scale with the corpus
- **An external surface that is pinned** — the command set, limits, routes, error codes, configuration keys and accepted format versions are described in `spec/` and held byte-exact by a test

## Upgrade actions required

Read this section before upgrading. The rest of the notes are informational.

### Replication may stop on a configuration that previously appeared healthy

Replication now fails closed on a binlog event it cannot apply and cannot prove harmless to skip. Previously such an event was silently ignored, so the index diverged from MySQL while `replication_state` stayed `running` and `/health/ready` stayed `ready`.

The affected settings are:

| Setting | What was happening | What happens now |
|---|---|---|
| `binlog_transaction_compression=ON` (MySQL 8.0.20+) | Whole transactions arrive as one payload event and were dropped in full | Replication stops with an undecodable-event error |
| `gtid_mode` not `ON` | Anonymous transactions applied their rows under the previous transaction's GTID | Replication stops before applying them |
| `LOAD DATA INFILE` on a replicated table | The applying statement was skipped | Replication stops |
| `binlog_row_value_options=PARTIAL_JSON` | Partial JSON row images were dropped | Replication stops |
| MariaDB compressed binlog events | Dropped | Replication stops |
| A binlog gap the source declared (`INCIDENT_EVENT`) | Committed across the gap and advanced past it | Replication stops before the gap |

**If your deployment uses any of these, its index is already wrong.** Stopping is the correction, not the regression. Recovery is `SYNC` for every replicated table, which rebuilds past the event; changing the server setting alone does not help, because the event that stopped the stream stays in the binlog.

### Configurations that no longer start

| Configuration | Why |
|---|---|
| `api.http.bind` non-loopback with an empty `api.admin_token` | The token rule previously looked only at the TCP listener, so an unauthenticated administrative HTTP surface could start |
| A `MYSQL_PASSWORD` or `MYSQL_ROOT_PASSWORD` still holding its `.env.example` placeholder | Starting on a credential published in this repository |
| A `time`-typed `required_filters` value outside MySQL's `TIME` range of ±838:59:59 | The value cannot be compared; it was previously passed through and clamped |
| A filter declared `type: float` | A result set renders `FLOAT` to six significant digits, so `16777217` reads back as `16777200` while the row image carries `16777216`. The digits are not in the text at all, so no normalization can reconcile the two |

### Columns now refused when replication starts

Every column named by `primary_key`, `text_source` or a filter is checked against `SHOW FULL COLUMNS`, and refused when the initial snapshot and the binlog row image would not render it identically. Previously the mismatch was silent: the same row became two documents, or the initial load aborted partway with no way to backfill.

Refused: `FLOAT`; `JSON`, `GEOMETRY` and its subtypes, `VECTOR`; any `ZEROFILL` column, whose result set carries the padded digits and whose row image carries the unpadded number; and any declared type this build cannot decode from a row image. The existing refusals for `BINARY`/`BLOB` and non-UTF-8 collations are unchanged.

Accepted, because both paths render them identically: the integer widths, `DECIMAL`, `DOUBLE`, `DATE`, `DATETIME`, `TIMESTAMP`, `TIME`, `YEAR`, `BIT`, `CHAR`, `VARCHAR`, the `TEXT` family, `ENUM` and `SET`. `TIME` and `BIT` are newly consistent — a `TIME(n)` primary key previously yielded `12:00:00.500` from the snapshot and `12:00:00.500000` from the binlog, and a `BIT` primary key yielded raw bytes against a decimal string, so an UPDATE reached neither the existing document nor deleted it.

### OPTIMIZE needs more free memory

The admission estimate charged 5% of index memory. Measurement shows the resident set grows by close to a second copy of the index whatever batch size the run uses, because a rebuilt posting list does not fit the hole the original left. The estimate now charges the rebuild in full, so `OPTIMIZE` requires roughly 2.1× index memory free and refuses otherwise. It previously admitted runs that were then killed by the kernel.

### A dump is matched to a table by its qualified name

The compatibility check a dump load runs against the running configuration identified a table by its bare name. Everything else in the server identifies a table by `database.table`, and configuration load permits the same bare name in two databases, so with `db1.articles` and `db2.articles` configured, a dump entry for `db2.articles` was compared against `db1.articles`.

Where the two tables' n-gram settings happened to agree, the check passed and an index built for one table was accepted onto the other: the documents were present, every search generated n-grams of the other size, and the result was an empty result set with no error anywhere. Where the settings differed, a correct dump was refused.

The check now compares qualified names, and a mismatch message names the qualified table. No artifact an earlier release wrote becomes unreadable: a table entry that records no database has it filled from the dump's own `mysql.database` when the config section is decoded, so it resolves by qualified name like any other.

**If you run more than one database and restore dumps, verify what is actually in your index before upgrading.** A restore that silently produced a wrong index does not repair itself; rebuild with `SYNC`.

### Rate limiting is now shared across protocols

A client drew from one token bucket per protocol, so a configuration of `capacity: N` admitted up to `2N` burst per client address when both protocols were used, and a runtime `SET api.rate_limiting.*` reached only TCP. One bucket is now shared. A deployment sending traffic over both protocols will see its accepted rate halve; raise `capacity` and `refill_rate` if the doubled figure was what you wanted.

## Behavior changes

### Search results

- **A query returns the same documents whichever path serves it.** The exact-text guard for mixed CJK/ASCII terms was applied on two of the four execution paths, so enabling synonyms or using boolean syntax added false positives. It now runs on all four.
- **`NOT` terms are verified against stored text** under the configured `memory.verify_text` policy, on both the clause form and the AST form. A document was previously excluded on an n-gram match alone, so a body containing `ab` and `bc` but not `abc` was dropped from `... NOT 'abc'`.
- **Floating-point `FILTER` equality compares the stored representation exactly.** It previously depended on which filter path ran: a filter combined with a range filter tolerated a 1e-9 difference while the same filter alone did not, so adding a filter that can only remove rows could add one. Ordering comparisons are unchanged and still tolerant.
- **Default sorting is defined for a mixed primary key.** A `VARCHAR` primary key holding both numeric and non-numeric values broke the comparator's transitivity, which is undefined behavior; both sort paths now derive one key space and agree. Ordering for a purely numeric or purely non-numeric primary key is unchanged.
- **`api.max_query_length` counts characters**, the unit the configuration schema, the error message and the sample configuration all state. It was enforced in bytes, so a Japanese query was rejected at roughly a third of the configured length.

### HTTP surface

- **`GET /config` and `GET /replication/status` require a bearer token** when `api.admin_token` is set, as the TCP equivalents always did.
- **The open health routes no longer carry replication detail.** The binlog position, its counters and the schema-incompatibility flag moved behind the token; `/health/detail` served the same state the gated routes protect.
- **A replication fault is named by code on an open route**, not by the MySQL error text, which disclosed the replication account name and the address MySQL sees. The verbatim message remains available with credentials and in the log.
- **`{"sort":{"column":"id"}}` names a column.** It was rewritten to the primary key whatever the primary key was called. Omit `column` for the primary key, matching `SORT ASC`/`SORT DESC` on TCP.
- **`SORT _score` rejections carry the TCP error codes** — 3007, 4 and 4007 rather than a single 2, which also brings them back inside the range this project assigns to query errors.

### Error codes that changed

Two conditions moved to the range this project assigns to their module. A client branching on the numeric code needs updating.

| Condition | Was | Now |
|---|---|---|
| Document not found, on TCP `GET` and HTTP `GET /tables/{t}/{pk}` | 8 `kNotFound` (General) | 4004 `kIndexDocumentNotFound` |
| `SET` naming an unknown variable | 2 `kInvalidArgument` (General) | 1008 `kConfigUnknownVariable` |
| `SET` naming a variable that needs a restart | 2 `kInvalidArgument` (General) | 1009 `kConfigVariableNotMutable` |

1008 and 1009 are new; the registry goes from 127 codes to 129. No existing code was renumbered or removed.
- **`/health/live` and `/health/ready` are not rate limited**, so a prober cannot be answered with 429.
- **`/health/detail` no longer reports a resync as a replication outage**, and a sync-induced pause is distinguishable from a disconnection.

### Replication and loading

- **Membership in the index is decided by one rule.** The initial-load SELECT and the binlog evaluator implemented the `required_filters` predicate separately. Text is now compared as bytes on both sides, so a filter of `status = 'Published'` no longer admits `'published'` at load under a case-insensitive collation and then deletes it on its first update. A `time` filter is written as a clock literal rather than a bare number MySQL reads as packed `HHMMSS`, and a `timestamp` filter compares epochs rather than passing a bound through `FROM_UNIXTIME`, which returned NULL for a pre-epoch value and made the load report success over zero rows.
- **A configured table named anywhere in a `DROP TABLE` list is detected.** Only the first name was examined, so `DROP TABLE other, configured` left the index serving deleted documents while the GTID advanced past the DDL.
- **A dump written by v1.5.4 or later restores.** A zero `header_size`, which every release through v1.5.3 wrote, is recognised; a dump that records no MySQL source server UUID is treated as source-unknown rather than source-mismatched, which is what every released version writes. A dump recording a UUID that differs is still refused. A dump written by v1.3.2 or earlier remains unreadable: its posting lists carry the opposite byte order with nothing in the artifact to distinguish them.
- **A dump too large for `dump.restore_memory_budget_mb` is refused before it is decoded**, returning the documented read error instead of being killed by the kernel.

### Observability

- **TCP `INFO` and HTTP `/info` and `/metrics` share one memory snapshot, rebuilt at most once a second.** `INFO` walked the whole corpus per poll while holding a lock replication needs; the interval is what bounds that cost, and one second already caps a polling client at one walk per second whatever its request rate. HTTP served the same figures from a 30-second snapshot, which is long enough to mislead an operator reading memory to decide whether a server is near its limit. Both surfaces now answer under the same rule, and a caller watching for a change has to allow for the interval.
- **Thread pool gauges on `/metrics` report live state.** `mygramdb_thread_pool_queue_depth`, `_queue_capacity` and `_workers` were permanently zero while the pool was really saturating and really rejecting requests.
- **An `AUTH` command is redacted from the log on the parser's own verdict.** A quoted or Unicode-space-prefixed `AUTH` bypassed the previous check and logged its token.

### Docker

- **The sample stack publishes MySQL on `127.0.0.1`.** It published on every interface, exposing MySQL root with the password committed in this repository. The backend reaches MySQL over the bridge network, so the publish exists only for a local client.
- **A password containing a backslash generates a config the container can parse.** The entrypoint wrote one backslash where the YAML escape needs two, leaving an invalid escape sequence in the generated file. The doubling only worked on `awk` implementations that read the replacement loosely, so the container image — which runs the strict reading — refused to start on such a password.

## Performance

Each of these was measured before and after; the measurements are kept as load-tier tests asserting ratios rather than durations, so a regression fails in the suite rather than in production.

- **Highlighting** performed one full document normalization per grapheme unit, so a 10 KB body with `LIMIT 100` ran roughly a million normalization passes on the request thread. The work now follows the match count and the configured snippet size.
- **A boolean `NOT`** materialized and sorted the entire corpus on every request; it now uses the same exclusion step the clause form uses.
- **A threshold search** materialized every candidate posting list at once.
- **`SORT _score` validation** was two implementations of about 85 and 65 lines; it is now one.

## Internal changes with no client-visible effect

- The HTTP surface reuses the request pipeline for quoting, table-name resolution, filter parsing, sort and highlight parsing, and limit and offset validation, rather than implementing them a second time. Both external-surface goldens are byte-identical across this change.
- Filter index bitmaps are owned through the shared RAII type, and an allocation failure is reported rather than silently dropping a document from a filter's results.
- Undefined behavior fixed in three places: a comparator reading a live atomic during `std::sort`, an out-of-bounds read on `DECIMAL` metadata a server would never emit, and a `bool` read directly from an untrusted dump.

## Specification

`spec/` is new and is the normative description of the external surface: the TCP command set, the HTTP routes, the error codes, the configuration keys and the persistence-format acceptance policy. Every claim names the file that implements it, and the symbol as well where the file is large, so it can be rechecked against the code rather than taken on trust.

Citations carry no line numbers. A line number drifts on any edit above the line it names, silently and in bulk, and the stale result still reads like evidence. `make spec-check` verifies that every cited path is a tracked file, that no citation carries a line anchor, and that a cited symbol appears in the file it is cited to.

Two generated goldens accompany it. `spec/surface.snapshot.txt` is what the server prints for the new `--print-surface` flag; `spec/response-shapes.snapshot.txt` records what a representative request set returns on both protocols. A diff in either means the external surface moved, which is how the changes above were bounded.

`tests/compat/` holds dumps produced by the v1.3.2, v1.5.4, v1.6.1 and v1.9.0 writers, so a change that stops reading an earlier release's artifact fails the suite.
